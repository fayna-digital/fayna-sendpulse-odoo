## Загальні правила (обов'язкові)

1. Правити лише файли, названі в завданні. Нічого не «покращувати» дотично.
2. Стиль репо: одинарні лапки, рядок ≤ 100 символів, `ruff check` і
   `ruff format --check` по модулю — чисті.
3. **Жодних AI-підписів** — ні в коді, ні в коментарях, ні в тексті коміту.
   Не згадувати модель чи інструмент.
4. Стандартна бібліотека: `hmac`, `hashlib`, `secrets`. Нових зовнішніх
   залежностей не додавати.
5. Порівняння секретів і підписів — **тільки** константним часом
   (`hmac.compare_digest`). Ніколи `==`.
6. Відхилення запиту — **до** будь-якого `create`/`write` у БД.
7. 🔴 **Заборонено копіювати код з OCA або Odoo Enterprise.** OCA під AGPL-3,
   Enterprise — пропрієтарний, наш модуль під OPL-1. Механіку звірено, але
   реалізація має бути власна, за специфікацією провайдера.

# Б-2 · Telegram: `secret_token` замість токена в URL

**Пріоритет P1, найтонше завдання пакета.**

## Навіщо

Повний Telegram bot-токен зараз лежить у **шляху** вебхука:
`/bridge/telegram/webhook/<token>`. Наслідки заміряні в аудиті: **34** входження
в `access.log` nginx (плюс ротовані `.gz`), запис у `odoo.log` щогодини, і той
самий токен у полі `heal_url` у БД відкритим текстом. Telegram — **єдиний
реально підключений канал** на проді, тобто це витік, який триває зараз.

## Підтверджена механіка

Telegram Bot API приймає в `setWebhook` параметр `secret_token`; після цього
кожен апдейт приходить із заголовком `X-Telegram-Bot-Api-Secret-Token`.
Механіку звірено з чужою живою Odoo-реалізацією (OCA `mail_gateway_telegram`) —
вона робить саме так. Код звідти **не брати**, лише підтвердження підходу.

## Файли

- `models/channel_backend.py`
- `controllers/main.py`
- `tests/test_operator_end_to_end.py`
- новий `migrations/17.0.1.2.0/post-migrate.py`
- `__manifest__.py`

## Крок 1 — нове поле `webhook_path_id`

У `models/channel_backend.py`:

- додати `webhook_path_id = fields.Char(...)`, індексоване (`index=True`),
  з міткою і `help` українською;
- додати SQL-обмеження унікальності на це поле. У моделі зараз
  **немає** `_sql_constraints` — секцію треба створити. Обмеження має
  дозволяти NULL (не-Telegram backend його не мають), але забороняти дублі
  непорожніх значень;
- значення генерувати `secrets.token_urlsafe(24)`. Модуль `secrets`
  у файл **не імпортовано** — імпорт додати;
- у моделі **немає** override `create`. Додати його
  (`@api.model_create_multi`, приймає список словників) так, щоб
  `webhook_path_id` заповнювався для нових записів, якщо його не передали.
  Значення не перегенеровувати, якщо воно вже є.

## Крок 2 — реєстрація вебхука

Переписати `register_telegram_webhook()` (`channel_backend.py`, приблизно
рядок 592):

- згенерувати секрет `secrets.token_urlsafe(32)` і зберегти в
  `webhook_secret` (якщо його ще немає — не перезаписувати наявний без потреби,
  бо це розсинхронізує вже зареєстрований вебхук);
- переконатись, що `webhook_path_id` заповнений; якщо ні — згенерувати;
- будувати URL як `<base_url>/bridge/telegram/webhook/<webhook_path_id>` —
  **без токена**;
- у виклик `setWebhook` додати параметр `secret_token` поруч із `url`;
- 🔴 **прибрати логування URL.** Зараз рядок ~614 друкує
  `'Channel Bridge: Telegram webhook set to %s', webhook_url` — тобто пише
  токен у лог. Замінити на повідомлення без URL: факт успіху + `self.id`.

## Крок 3 — обробник вебхука

У `controllers/main.py`:

- роут `'/bridge/telegram/webhook/<token>'` замінити на
  `'/bridge/telegram/webhook/<webhook_id>'`;
- пошук backend робити за `webhook_path_id`, а не перебором усіх telegram-
  backend із порівнянням токена. Наявний `_find_backend_by_token` **не
  видаляти** — він може знадобитись; але з обробника більше не викликати;
- після знаходження backend звірити заголовок
  `X-Telegram-Bot-Api-Secret-Token` з `backend.webhook_secret` через
  `hmac.compare_digest`;
- 🔴 **порожній `webhook_secret` = 401**, а не «пропустити». (У чужій
  AGPL-реалізації тут навпаки — при порожньому секреті вона пропускає будь-що.
  Це її вада, повторювати не можна.);
- відхилення — через наявний хелпер `_reject_unauthorized`, до будь-якого запису.

## Крок 4 — міграція

Новий файл `migrations/17.0.1.2.0/post-migrate.py`:

- у `__manifest__.py` підняти `version` до `17.0.1.2.0`;
- функція `migrate(cr, version)`: для наявних записів `channel_backend` із
  `service = 'telegram'` і порожнім `webhook_path_id` згенерувати значення;
- ідемпотентно: повторний запуск не падає і нічого не псує;
- SQL параметризований, **без f-string**;
- повторну реєстрацію вебхука в міграції **не робити** — це мережевий виклик,
  він лишається за кнопкою і кроном;
- логувати кількість оновлених записів, з префіксом `Channel Bridge:`.

## Крок 5 — правка T-01 (робити в цьому ж проході)

# Б-1.1 · Загартування перевірки підпису Meta

**Робити після Б-2.** Файл: `controllers/main.py`.

## Навіщо

Звірка з реалізацією самого Odoo показала крок, якого в нас немає: **формат
заголовка перевіряють до обчислення HMAC**. Ми ж рахуємо HMAC на будь-який
рядок, що прийшов.

## Що зробити

У хелпері `_verify_hmac` (або в Meta-гілці, що його кличе) відкидати свідомо
невалідний підпис **до** обчислення:
- не починається з `sha256=` → False;
- довжина не дорівнює 71 символу (`sha256=` плюс 64 hex-символи) → False.

⚠️ **Тільки для Meta-гілки** (`X-Hub-Signature-256`, тобто messenger і
whatsapp). Для Viber, TikTok і LiveChat формат заголовка інший — там ця умова
відрізала б валідні запити. Якщо `_verify_hmac` спільний для всіх каналів,
зробити перевірку формату окремим кроком у Meta-обробниках, а не всередині
спільного хелпера, або додати явний прапорець.

## Verify для Б-1.1

- підпис без префікса `sha256=` → 401;
- підпис із правильним префіксом, але обрізаний → 401;
- наявні тести `TestWebhookAuth` (T-10, T-11, T-15) лишаються зеленими;
- Viber / TikTok / LiveChat гілки не зачеплені перевіркою довжини.

# Б-6 · Дедуп по порожньому id ковтає повідомлення

**Робити після Б-1.1.** Файл: `controllers/main.py`.

## Навіщо

Три місця дедупу — приблизно рядки **83**, **236**, **315** (після Б-2 і Б-1.1
номери зсунуться, шукати за змістом) — виконують пошук
`('provider_message_id', '=', provider_message_id)` **без перевірки на
порожнечу**. Якщо провайдер не дав ідентифікатора (у Viber `message.token`
буває відсутній), пошук по порожньому рядку знайде **будь-який** попередній
запис із порожнім id і поверне «duplicate, skipping». Справжнє повідомлення
клієнта зникне, і навіть сліду в ERROR-лозі не лишиться.

## Що зробити

У всіх трьох місцях виконувати дедуп **лише якщо `provider_message_id`
непорожній**. Якщо порожній — дедуп пропустити, повідомлення обробити як нове,
і записати `_logger.warning` з префіксом `Channel Bridge:`, назвою каналу і
поясненням, що провайдер не дав ідентифікатора.

## Verify для Б-6

- усі три пошуки за `provider_message_id` стоять під умовою непорожності;
- новий тест: два різні вхідні з порожнім `provider_message_id` дають **дві**
  окремі розмови/записи, жодного «skipping»;
- повний набір модуля зелений.

# Прогін — після кожного із трьох завдань окремо

Середовище піднімається окремо від репо. Постійний Odoo займає порт 8069, тому
**кожному прогону давати власний порт** — інакше тестовий HTTP-сервер не
підніметься (`Address already in use`), запит піде в чужий інстанс і поверне
хибний **401**, який виглядатиме як провал автентифікації. Ми на це вже
наступали.

Прогін робити `docker exec` на **запущеному** контейнері — не
`docker compose run --rm`, він зупиняє контейнер (див. `docs/DEPLOYMENT.md`).
База — щоразу **нова й чиста**. Ключі: `-i fayna_channel_bridge --test-enable
--test-tags /fayna_channel_bridge`, власний `--http-port`, `--stop-after-init`.

Критерій приймання кожного кроку: `0 failed, 0 error(s) of N tests`, код виходу 0.
