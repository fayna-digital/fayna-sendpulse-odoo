## 1. Objective (мета і межі)

**Що:** автономний omnichannel-міст «чат-провайдер ↔ Odoo 17 Discuss» без зовнішнього
посередника. Приймає вхідні з Telegram/Instagram/Messenger/WhatsApp/Viber/TikTok/LiveChat,
створює розмову і Discuss-канал, дає оператору відповісти клієнту через власний транспорт.

**Для кого:** CampScout (дитячі літні табори PL), Fayna Digital. Оператори — не технічні
користувачі, працюють через UI.

**Межі (що НЕ входить):** AI-асистент, drip-кампанії, A/B шаблони, lead magnet, RODO-аудит
інших модулів — це сфера знятого SendPulse-модуля і не переноситься.

**Успіх (DoD):** вхідне з будь-якого каналу з'являється в Discuss з ідентифікованим
контактом і оператором-учасником; відповідь оператора доставляється клієнту; вебхуки
автентифіковані; секрети не світяться; мульти-акаунтність і OAuth-онбординг працюють;
UI зручний; CI ганяє тести з coverage ≥80%; деплой тільки з git-коміту.

### 2.4 Підключення каналів — еталон SendPulse

> **Зразок затверджено власником 30.08.2026** за живими екранами SendPulse
> (галерея каналів → сторінка «Підключити канали» → OAuth Meta → вибір Сторінок →
> рев'ю дозволів → вибір Бізнес-менеджерів). Інваріант еталона:
> **користувач жодного разу не бачить ні токена, ні URL вебхука** — він бачить
> свої сторінки людськими назвами і ставить галочки.

**Зразок в Odoo Community:** `google.gmail.mixin` (`google_gmail`) — єдиний штатний
OAuth-патерн, доступний нам. `social_facebook` — Enterprise-only, у нашій збірці
відсутній [ПЕРЕВІРЕНО 30.08: `ls addons | grep ^social` → лише `social_media`;
моделей `social.*` у БД 0]. Тому будуємо **за контрактом gmail-міксина**:
`_compute_auth_uri()` → `action_connect()` повертає `ir.actions.act_url` →
контролер `/bridge/oauth/<provider>/callback` ловить `code` → `_exchange_code()` →
`_fetch_accounts()` → майстер вибору → створення `channel.backend`.

#### 2.4.1 Два класи підключення (не один)

Вимога «без пошуку токенів» має два втілення, бо провайдери різні:

| Клас | Канали | Механіка | Чому так |
|---|---|---|---|
| **OAuth** | Messenger, Instagram, WhatsApp, TikTok | кнопка «Увійти через…» → вибір активів → 0 ручного вводу | провайдер має OAuth-діалог |
| **Token** | Telegram, Viber | одне поле + миттєва валідація + автопідписка вебхука | **OAuth для ботів не існує** — токен видає BotFather; SendPulse робить так само |

🔴 **Не намагатись зробити OAuth для Telegram** — його немає в Telegram Bot API.
Обіцяти в UI «підключення без токена» для Telegram = обіцяти неможливе.

#### 2.4.2 Потік OAuth-каналу (6 кроків еталона)

| Крок | Що бачить користувач | Що робить модуль |
|---|---|---|
| 1 | Галерея карток каналів, на кожній «Підключити» | kanban `channel.provider` (каталог, `noupdate`) |
| 2 | Сторінка «Підключити канали»: список ліворуч, опис + одна кнопка праворуч | форма з `channel.provider`, кнопка → `action_connect()` |
| 3 | Діалог провайдера «Continue as …» | `ir.actions.act_url` на `_compute_auth_uri()` зі `state`=CSRF |
| 4 | Вибір Сторінок: «усі теперішні й майбутні» / «лише обрані» | callback → `_exchange_code()` → `_fetch_accounts()` |
| 5 | Рев'ю запитаних дозволів | scopes оголошені декларативно на `channel.provider` |
| 6 | Чекбокси Бізнес-менеджерів / Сторінок із назвами й аватарами | wizard `channel.connect.wizard` → `channel.backend` на кожен обраний актив |

#### 2.4.3 Потік Token-каналу (екран Telegram)

Одне поле з плейсхолдером формату, кнопка «Підключити», лінк «Як отримати ключ
доступу?». Після натискання — синхронна валідація; помилка показується тостом
одразу, не при першому повідомленні.

#### 2.4.4 Матриця каналів (звірено за живими екранами SendPulse 30.08.2026)

| Канал | Метод | Передумови / блокери, показані ДО кнопки |

#### 2.4.5 Один декларативний провайдер, не сім екранів

🔴 **Архітектурне рішення:** не писати сім окремих майстрів. Модель
`channel.provider` (каталог, `noupdate="1"`) несе **декларативні** поля, а UI —
один узагальнений:

| Поле | Призначення |
|---|---|
| `connect_method` | `oauth` · `token` · `widget` |
| `precondition_ids` | передумови, які треба виконати ДО (бізнес-акаунт, відв'язаний номер) |
| `region_blocklist` | регіони, де канал недоступний (TikTok: ЄЕЗ/ЄС, США) |
| `consent_required` / `consent_url` | чекбокс згоди, що гейтить кнопку (WhatsApp) |
| `cost_warning` | сталі витрати провайдеру (Viber ~100 EUR/міс) |
| `side_effect_warning` | побічний ефект (WhatsApp: втрата мобільного застосунку) |
| `help_url` | «Як отримати ключ доступу?» / «Докладніше» |
| `fallback_method_ids` | запасні шляхи входу (IG: Instagram login, старий FB Business) |
| `token_placeholder` / `token_regex` | формат токена для підказки і клієнтської валідації |

Додати новий канал = **рядок даних, не новий код**.

## 10. Критерії приймання (DoD)

1. **T-01 (наскрізний сценарій) проходить** через HTTP-контролер: вебхук → розмова →
   оператор-учасник → відповідь → доставка. (На поточному коді T-01 **падає** — це доказ,
   що гейт справжній.)
2. Усі тести з `Verify` у цьому ТЗ проходять у CI (coverage ≥80%).
3. CI test-job **required** у branch protection; деплой тільки з git-коміту.
4. Секрети не світяться в логах/БД; вебхуки автентифіковані.
5. Мульти-акаунтність і OAuth-онбординг працюють; UI зручний (UX-01..UX-08).
