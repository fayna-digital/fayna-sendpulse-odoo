## Загальні правила (діють на ВСІ завдання)

1. Правити лише названі файли. Не «покращувати» дотично.
2. Стиль репо: одинарні лапки, рядок ≤ 100 символів, `ruff check` і
   `ruff format --check` чисті.
3. **Жодних AI-підписів** — ні в коді, ні в коментарях, ні в тексті коміту.
4. Не додавати зовнішніх залежностей. `hmac`, `hashlib`, `secrets` — стандартна

5. **Не ламати наявні тести.** Після кожного завдання весь набір модуля мусить
   лишатись зеленим. Команда прогону — в кінці документа.
6. Порівняння підписів — **лише** `hmac.compare_digest`. Ніколи `==`: звичайне
   порівняння рядків відкриває timing-атаку.
7. Відхиляти запит **до** будь-якого запису в БД. Це буквальна вимога NFR-01,
   а не побажання: інакше неавтентифікований POST уже лишив слід.

**Файл:** `addons/fayna_channel_bridge/controllers/main.py`

**Проблема.** Сім роутів, **усі** `auth='public'`, `csrf=False`, обробка під

**Що зробити.**

1. Додати приватний хелпер (один на контролер): приймає сире тіло

   `sha256=<hex>`, HMAC-SHA256 від сирого тіла на секреті застосунку. Секрет —

3. **Viber**: заголовок `X-Viber-Content-Signature`, HMAC-SHA256 від сирого тіла

4. **TikTok, LiveChat**: якщо провайдер підпису не дає — вимагати спільний секрет

   `compare_digest`. Порожній секрет = 401.
5. Невалідний або відсутній підпис → відповідь зі статусом **401** до будь-якого
   `create`/`write`. Логувати `_logger.warning` з префіксом `Channel Bridge:`,
   `remote_addr` і назвою каналу — але **без самого підпису й без тіла запиту**.
6. Після успішної валідації відповідь **завжди 200**, помилки обробки — в лог
   (це FR-31: інакше провайдер зациклить ретраї).

⚠️ Сире тіло читати **до** `json.loads` і підписувати саме його. Підпис від
перезібраного JSON не збігається ніколи — це найчастіша помилка в цій задачі.

**Verify:**
- пошук `compare_digest` по `controllers/main.py` → щонайменше один збіг

## Б-2 · F-08 (P1) · Telegram: `secret_token` замість токена в URL + правка T-01

**Файли:** `controllers/main.py`, `models/channel_backend.py`,
`tests/test_operator_end_to_end.py`, нова міграція, `__manifest__.py`.

**Проблема.** Повний bot-токен лежить у шляху вебхука
(`/bridge/telegram/webhook/<token>`). Наслідки, заміряні в аудиті: **34**
входження в `access.log` nginx, плюс ротовані `.gz`, плюс Referer, плюс будь-який
проміжний проксі. Той самий токен ще й пишеться в поле `heal_url` у БД.

Telegram Bot API має штатний механізм: `setWebhook(secret_token=...)`, після чого
кожен апдейт приходить із заголовком `X-Telegram-Bot-Api-Secret-Token`.

**Що зробити.**

1. Роут змінити на **непрозорий ідентифікатор**, не токен:
   `/bridge/telegram/webhook/<webhook_id>`, де значення — нове поле
   `channel.backend.webhook_path_id` (`fields.Char`, індексоване, унікальне),
   заповнюється `secrets.token_urlsafe(24)` при створенні backend.
2. `register_telegram_webhook()` (`channel_backend.py:592`):
   - згенерувати `secret_token` (`secrets.token_urlsafe(32)`) і покласти
     у `webhook_secret`;
   - будувати URL з `webhook_path_id`, а не з токена;
   - передати `secret_token` у тіло `setWebhook`;
   - **не писати URL у лог** — рядок 614 зараз друкує саме його; логувати лише
     факт успіху і id backend.
3. Обробник `telegram_webhook`: шукати backend за `webhook_path_id`, далі звіряти
   заголовок `X-Telegram-Bot-Api-Secret-Token` з `backend.webhook_secret` через
   `compare_digest`. Розбіжність або відсутність → 401 до запису.
4. Міграція `migrations/17.0.1.2.0/post-migrate.py` (**версію в маніфесті підняти
   до `17.0.1.2.0`**): наявним telegram-backend без `webhook_path_id` згенерувати
   його. Ідемпотентно, параметризований SQL, без f-string у запитах.
   Повторну реєстрацію вебхука в міграції **не робити** — це мережевий виклик;
   лишити наявній кнопці й крону.
5. **T-01**: змінити URL у методі `_incoming` на новий шлях і додати заголовок із
   секретом. Асерти не чіпати — жодного.

⚠️ Після цієї зміни старий URL перестає працювати. На проді потрібна повторна
реєстрація вебхука — це операція власника, у код її не зашивати.

**Verify:**
- пошук `webhook/<token>` у `controllers/main.py` → нуль збігів
- T-01 зелений на новому шляху, усі 8 асертів на місці
- новий тест: невалідний `secret_token` → 401, `channel.message` = 0 (T-13)
- пошук `webhook set to` у `models/channel_backend.py` → нуль збігів (T-32)

## Б-1.1 · Загартування підпису Meta (з реалізації самого Odoo)

**Файл:** `addons/fayna_channel_bridge/controllers/main.py`
**Робити ПІСЛЯ Б-2**, бо той самий файл.

**Звідки взялось.** Звірка з двома живими Odoo-реалізаціями (30.08, GitHub API):
OCA/social `mail_gateway_whatsapp` і власний `whatsapp/controller/main.py` Odoo.
Обидві підтверджують нашу механіку (HMAC-SHA256 сирого тіла, `X-Hub-Signature-256`,
формат `sha256=<64 hex>`). Але в Odoo є крок, якого в нас немає.

**Що зробити.** У хелпері `_verify_hmac` перед обчисленням HMAC відкидати
свідомо невалідний заголовок:
- підпис не починається з `sha256=` → False;
- довжина не дорівнює 71 символу (`sha256=` + 64 hex) → False.

Це раннє відсіювання сміття: не рахуємо HMAC на кожен випадковий рядок.

⚠️ Перевірку довжини застосовувати **лише до Meta-гілки** (`X-Hub-Signature-256`).
Для Viber, TikTok і LiveChat формат заголовка інший — там ця умова відрізала б
валідні запити.

🔴 **Копіювати код Odoo або OCA заборонено.** OCA під AGPL-3, Odoo Enterprise —
пропрієтарний; наш модуль під OPL-1. Ці джерела — лише підтвердження механіки,
реалізація має бути власна, за специфікацією Meta.

**Verify:**
- підпис без префікса `sha256=` → 401
- підпис правильного префікса, але обрізаний → 401, і HMAC не обчислювався
- наявні тести `TestWebhookAuth` лишаються зеленими

### Чим доведено кожен рядок

- **«Підключений на проді»** — зведена таблиця аудиту, рядок «Не працює»:
  «Viber, TikTok, Facebook — не налаштовані взагалі». Живі 13 звернень з 27.08
  прийшли через Telegram.
- **Viber без підтвердження** — пошук `_verify_update` по OCA/social дав рівно
  **чотири** файли: `mail_gateway_abstract`, `mail_gateway_whatsapp`,
  `mail_gateway_telegram`, `mail_gateway/controllers/gateway.py`. Viber серед
  них немає.
- **TikTok без реалізації** — три різні запити до GitHub
  (`tiktok webhook signature odoo`, `odoo tiktok webhook controller`,
  `tiktok webhook verify signature hmac`) дали 0, 0 і 24 збіги; усі 24 —
  дрібні непрофільні проєкти, жодного під Odoo.

### Правило для виконавця

🔴 **Не вигадувати механізм там, де його не підтверджено.** Для TikTok і
LiveChat лишається спільний секрет у заголовку `X-Bridge-Secret`, як у Б-1.
Для Viber наша схема лишається, але позначена як **непідтверджена** — перед
підключенням каналу її треба звірити з документацією Viber.

Ці три канали зараз **не несуть живого ризику**, бо не підключені. Уточнення їх
механіки — робота Етапу 3, коли канали справді вмикатимуть, і робиться вона за
документацією провайдера, а не за здогадом.

### Чого НЕ повторювати з чужих реалізацій

- 🔴 OCA `mail_gateway_telegram._verify_update`: при **порожньому**
  `webhook_secret` повертає `True`, тобто пускає будь-що. У нас порожній
  секрет = **401**.
- 🔴 OCA порівнює підписи через `==` (і в whatsapp, і в telegram) — не
  константний час. У нас `hmac.compare_digest`.
- Odoo Enterprise логує значення невалідного заголовка
  (`'Invalid signature header %r'`). Ми підпис у лог **не пишемо**.

Ліцензійно: OCA — AGPL-3, Odoo Enterprise — пропрієтарний, наш модуль — OPL-1.
Код звідти **не копіювати**; джерела правлять лише як підтвердження механіки.

## Команда прогону (обов'язкова після кожного завдання)

Середовище піднімається окремо від репо. Постійний Odoo займає порт 8069, тому
**кожному прогону давати свій порт** — інакше тестовий HTTP-сервер не підніметься
(`Address already in use`), запит піде в чужий інстанс і поверне хибний 401.

Прогін: `docker exec` на **запущеному** контейнері (не `docker compose run --rm` —
він зупиняє контейнер, див. `docs/DEPLOYMENT.md`), з окремою чистою базою,
ключами `-i fayna_channel_bridge --test-enable --test-tags /fayna_channel_bridge`,
власним `--http-port` і `--stop-after-init`.

Критерій приймання: `0 failed, 0 error(s) of N tests`, код виходу 0.
