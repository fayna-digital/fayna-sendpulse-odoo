# Пакет 3 — Візуалізація: UI оператора і підключення каналів

Етап 3 плану аудиту (частина UI). Базові документи:
`TZ_FAYNA_CHANNEL_BRIDGE.md` (вимоги UX-01…UX-18, FR-53, FR-66, FR-67),
`TEST_PLAN_FAYNA_CHANNEL_BRIDGE.md` (T-88…T-96, T-114…T-119, T-128…T-131).
Репо: `fayna-sendpulse-odoo`, гілка `feature/direct-transport`, Odoo 17.

**Виконувати після Етапу 2** (Пакети 1 і 2 — безпека).

## Стан на старті (звірено в коді 30.08.2026)

- у модулі **один** файл view — `views/channel_backend_views.xml`;
- меню лише два: корінь `menu_channel_bridge_root` і `menu_channel_bridge_backends`;
- для `channel.conversation` і `channel.message` **немає жодного** списку, форми
  чи меню — права доступу є, UI немає. Оператор не має де побачити ні розмов,
  ні журналу;
- моделі `channel.provider` не існує;
- у `__manifest__.py` секція `data` містить чотири файли.

Чотири завдання пакета чіпають **різні** файли, тому послідовність вільна.
Рекомендований порядок: **В-1 → В-2 → В-3 → В-4**.
Прогін тестів — після кожного завдання, чиста база, окремий порт.

## Загальні правила (обов'язкові)

1. Правити лише файли, названі в завданні; нові створювати там, де сказано.
2. **Стиль репо — одинарні лапки** (`pyproject.toml`,
   `[tool.ruff.format] quote-style = 'single'`). Масово перелапковувати файли
   заборонено — це роздуває диф і ховає справжню зміну.
3. Рядок ≤ 100 символів; `ruff check` і `ruff format --check` по модулю чисті.
4. **Жодних AI-підписів** — ні в коді, ні в коментарях, ні в комітах.
5. Нових зовнішніх залежностей і JS-бібліотек не додавати. Усе — штатними
   засобами Odoo 17 (list/form/kanban/search views, `ir.actions.act_window`).
6. Кожен новий XML-файл додавати в `data` у `__manifest__.py`, у правильному
   порядку (моделі й security раніше за views, що на них посилаються).
7. Не ламати наявні тести. Після кожного завдання набір модуля — зелений.

🔴 **Інваріант UX-14, діє на весь пакет:** на екранах підключення **ніде** не
показувати bot-токен, App Secret, `webhook_secret`, `webhook_path_id` чи URL
вебхука. Після Б-5 ці поля мають `groups=` адміністратора — не обходити це
обмеження і не виводити їх у нових view.

# В-1 · UI оператора: розмови і журнал

**Нові файли:** `views/channel_conversation_views.xml`,
`views/channel_message_views.xml`
**Правити:** `__manifest__.py` (секція `data`), `views/channel_backend_views.xml`
(лише додати пункти меню)

## Навіщо

Аудит, розділ відповідності стандарту Odoo: «лише `channel_backend_views.xml`;
`channel.conversation` і `channel.message` мають права доступу, але **жодного
списку, форми чи меню** — оператор не має UI». Тобто оператор бачить розмову
тільки якщо натрапить на неї в Discuss; журналу не бачить взагалі.

## Що зробити

### `channel.conversation`

- **list view**: канал (`service`), контакт (`name`), `partner_id`,
  `last_message_preview`, `last_message_date`, `stage`. Стадію показати як
  бейдж; прострочені/нові виділити декорацією (`decoration-*`) — без
  кастомного CSS.
- **form view**: шапка зі стадією (`statusbar` по `stage`), основні поля,
  вкладка з історією повідомлень — `One2many` на `channel.message` (UX-03).
  Якщо зворотного поля немає, додати його на `channel.message` як
  `Many2one` до розмови **лише якщо воно вже існує в моделі**; якщо ні —
  показати повідомлення відфільтровані за `provider_user_id` + `service`
  через окрему дію, а модель **не міняти** (зміна схеми — окреме рішення).
- **кнопка «Відкрити в Discuss»** (UX-04): відкриває `channel_id`.
  Якщо `channel_id` порожній — кнопку ховати.
- **search view**: фільтри за каналом, стадією, «є партнер / немає партнера»,
  групування за каналом і стадією.
- **`help` на action** (UX-06, T-93): порожній стан має пояснювати, що робити,
  а не бути порожнім екраном.

### `channel.message`

- **list view** (журнал): дата, `service`, `direction`, `state`,
  `provider_user_id`, `text_message` (обрізаний), `last_error`.
- **form view**: тільки читання по суті; `raw_json` показувати згорнутим.
- 🔴 `last_error` показувати можна — після Б-3 він замаскований. Якщо Б-3 ще
  не влито, **не виводити це поле** взагалі.
- **search view**: фільтри за напрямком, станом, каналом; групування за каналом
  і станом; фільтр «лише помилки» (`state = 'failed'`).

### Меню (UX-01, T-92)

Під наявним коренем `menu_channel_bridge_root` зробити три пункти в порядку:
1. **Розмови** → `channel.conversation`, доступ групі **Officer**;
2. **Журнал** → `channel.message`, доступ групі **Officer**;
3. **Канали** → наявний `action_channel_backend`, доступ **лише Administrator**
   (зараз пункт видно всім, хто має доступ до кореня).

Пункт «Канали» перевести на групу адміністратора через атрибут `groups`.

## Verify для В-1

- новий тест: користувач лише з групою Officer бачить пункти «Розмови» і
  «Журнал» і **не** бачить «Канали» (T-92);
- новий тест: `ir.actions.act_window` для розмов має непорожній `help` (T-93);
- усі три view відкриваються без помилок під обома ролями — перевірити
  installом модуля з `--test-enable` (помилка в XML валить установку);
- `ruff` і повний набір тестів зелені.

# В-2 · Модель-каталог `channel.provider`

**Нові файли:** `models/channel_provider.py`, `data/channel_provider_data.xml`
**Правити:** `models/__init__.py`, `__manifest__.py`,
`security/ir.model.access.csv`

## Навіщо

Рішення власника (зафіксоване 30.08): **не сім майстрів підключення, а один
декларативний каталог**. Новий канал має бути рядком даних, а не новим Python-
кодом (FR-67, T-127).

## Що зробити

Модель `channel.provider` — довідник, `_order` за послідовністю. Поля:

| Поле | Тип | Призначення |
|---|---|---|
| `name` | Char | назва каналу для людини |
| `service` | Selection | той самий список, що `SERVICE_SELECTION` у `channel_backend.py` — **перевикористати константу**, не дублювати |
| `sequence` | Integer | порядок у галереї |
| `connect_method` | Selection: `oauth` / `token` / `widget` | яким способом підключається |
| `token_placeholder` | Char | приклад формату ключа для поля вводу |
| `help_url` | Char | лінк «Як отримати ключ доступу?» (UX-11) |
| `description` | Text | що цей канал дає — показується праворуч у галереї |
| `precondition_ids` | One2many або Text | передумови, які треба виконати ДО підключення |
| `region_blocklist` | Char | регіони, де канал недоступний |
| `consent_required` | Boolean | чи гейтить кнопку чекбокс згоди |
| `cost_warning` | Char | попередження про платність |
| `side_effect_warning` | Char | попередження про побічні наслідки |
| `active` | Boolean | стандартне |

Обчислювані (не зберігати):
- `backend_id` / `is_connected` — чи є активний `channel.backend` із таким
  `service`;
- `status_label` — людський статус для картки.

`data/channel_provider_data.xml` — записи для **семи** каналів з
`noupdate="1"`: telegram, messenger, instagram, whatsapp, viber, tiktok,
livechat. Заповнити реальними значеннями:

- **telegram**, **viber** → `connect_method = 'token'`;
  🔴 у Telegram OAuth **не існує** — токен видає BotFather. Не писати в UI
  обіцянку «без токена» для Telegram;
- **messenger**, **instagram**, **whatsapp**, **tiktok** →
  `connect_method = 'oauth'` (сам OAuth у цьому пакеті **не реалізується**,
  див. В-4);
- **livechat** → `connect_method = 'widget'`, авторизація не потрібна;
- **whatsapp**: `consent_required = True`, `cost_warning` про платний тариф,
  `side_effect_warning` про втрату керування діалогами з мобільного застосунку;
- **tiktok**: `region_blocklist` — ЄЕЗ/ЄС і США; передумова «бізнес-акаунт».

Права доступу: читання — обом групам, запис — лише Administrator.

## Verify для В-2

- новий тест: у базі після установки рівно **7** записів `channel.provider`;
- новий тест (T-127): створення нового `channel.provider` рядком даних не
  потребує змін у Python — запис створюється і з'являється в галереї;
- `service` бере значення зі спільної константи, не з дубльованого списку
  (перевірити читанням коду);
- повний набір тестів зелений.

# В-3 · Галерея «Підключити канали»

**Новий файл:** `views/channel_provider_views.xml`
**Правити:** `__manifest__.py`, меню

## Навіщо

UX-09: «видно галерею карток усіх каналів з іконками і статусом
(підключено / ні)». UX-15: «блокери видимі на картці **ДО** натискання, а не в
помилці після». UX-16: «якщо кнопку заблоковано — видно ЧОМУ».

## Що зробити

- **kanban view** на `channel.provider`: картка на канал, у картці — назва,
  статус (підключено / не підключено), і **видимі блокери**: `cost_warning`,
  `side_effect_warning`, `region_blocklist`, позначка про згоду. Блокери
  показувати завжди, коли поле непорожнє (UX-15).
- **form view**: ліворуч опис (`description`), праворуч **рівно одна** головна
  дія (UX-10, T-115) — кнопка «Підключити». Другорядні дії робити не-primary.
- Якщо канал уже підключений — головна дія змінюється на «Перепідключити»
  або «Відкрити канал», але лишається **однією**.
- Лінк «Як отримати ключ доступу?» показувати для `connect_method = 'token'`,
  беручи URL із `help_url` (UX-11, T-116).
- Пункт меню «Підключити канали» під коренем, доступ **Administrator**.
- Іконки каналів класти в `static/description/` або
  `static/img/`; зовнішніх CDN не використовувати.

🔴 На жодному екрані цієї галереї не має бути токена, секрету чи URL вебхука
(UX-14, T-119).

## Verify для В-3

- новий тест (T-114): галерея показує **7** карток, у кожній видно статус;
- новий тест (T-115): на формі провайдера рівно **одна** primary-кнопка;
- новий тест (T-116): для token-каналу `help_url` непорожній;

**Правити:** `models/channel_provider.py`, `models/channel_backend.py`

## Що зробити

- Кнопка «Підключити» на token-каналі відкриває **wizard** з **одним** полем
  вводу ключа і плейсхолдером із `token_placeholder`. Більше жодного поля

  жодного ручного JSON і жодного URL вебхука).
- Після «Підключити»:
  1. створити або оновити `channel.backend` для цього `service`;
  2. записати ключ у відповідне поле;
  3. **одразу** викликати наявний `register_telegram_webhook()` для Telegram
     (для Viber — відповідний метод, якщо він є; якщо немає —
     **не вигадувати**, лишити backend створеним і показати, що підписку
     треба зробити окремо);
  4. показати результат користувачеві.
- **Помилки — людською мовою** (UX-12): відображати не сирий текст провайдера,
  а зрозуміле пояснення. Мапу типових причин зробити **декларативною**
  (словник у моделі), щоб додавання нової причини не потребувало правки логіки.
- Ніде не показувати згенерований `webhook_secret`, `webhook_path_id` чи
  підсумковий URL вебхука.

🔴 **OAuth у цьому пакеті НЕ реалізується.** Для каналів із
`connect_method = 'oauth'` кнопка має показувати зрозуміле повідомлення, що
підключення поки виконується адміністратором вручну. Реалізація OAuth потребує
реєстрації застосунку Meta, App Secret і рішення власника — це окреме ТЗ.

# Відомий конфлікт, який треба врахувати

**Мова інтерфейсу.** У модулі всі `string=` і `help=` написані **українською
напряму**. Тест T-95 вимагає англійських `msgid` і окремих `uk`/`pl` `.po`.
Це суперечність між поточним кодом і ТЗ, і вона стосується **всього** модуля,
а не лише нових view.

У цьому пакеті **нічого не перекладати** — писати нові рядки в тому ж стилі, що
наявні (українською), щоб не було двох стилів одночасно. Переклад — окреме
завдання Етапу 4 (i18n), робиться разом по всьому модулю.

# Прогін — після кожного з чотирьох завдань

Середовище окремо від репо. Постійний Odoo займає 8069, тому **кожному прогону
власний порт** — інакше тестовий HTTP-сервер не підніметься
(`Address already in use`) і запит піде в чужий інстанс.

`docker exec` на **запущеному** контейнері (не `docker compose run --rm`),
щоразу **нова чиста** база, ключі `-i fayna_channel_bridge --test-enable
--test-tags /fayna_channel_bridge`, власний `--http-port`, `--stop-after-init`.

⚠️ Помилка в XML валить **установку модуля**, а не окремий тест. Якщо прогін
падає на етапі loading — дивитись саме XML нових view, а не тести.

Критерій приймання кожного кроку: `0 failed, 0 error(s) of N tests`, exit 0.

# Що подати у звіті

1. По кожному з чотирьох завдань: файли і кількість змінених рядків.
2. Результат кожного `Verify:` — **командою і виводом**, не переказом.
3. Підтвердження, що `ruff format --check` чистий і диф не роздутий.
4. Скріншот або опис того, що реально видно на екрані галереї — бо XML може
   бути валідним, а екран порожнім.
5. Окремо назвати все, що зроблено **поза** цим документом, і чому.
