## Е-1 · Заголовки колонок обрізані

**Файл:** [`views/channel_backend_views.xml`](../addons/fayna_channel_bridge/views/channel_backend_views.xml)

### Обраний варіант і чому

Обрано варіант **«дати явну ширину або `optional="hide"` малозначущим колонкам»**:
колонку **«Пріоритет»** (`transport_priority`) позначено `optional="hide"`.

**Чому саме цей варіант:**

- Корінь проблеми (за завданням) — не довжина тексту, а те, що текстові колонки «Назва» і «Канал» забирають усю ширину, лишаючи булевим «Активний» і «Healthcheck» ~45 px. Перейменування не працює за визначенням.
- `transport_priority` — службова колонка (значення «own»/«direct»), яка для оператора-користувача мала цінність лише в адмін-контексті. Ховати її за `optional` — найменш інвазивний крок: вона **не видалена**, а доступна через меню «Колонки» (⋮) у списку, тож адміністратор може її повернути.
- Це звільняє ширину для двох булевих колонок, які тепер читаються повністю (див. Verify нижче).
- Альтернативу «винести булеві в форму, лишити один зведений індикатор» відхилено: вона змінює інформаційну модель списку і прибирає зручний швидкий огляд стану каналів. Альтернативу «обмежити ширину текстових колонок» відхилено: вона ризикує обрізати назви каналів.

### Verify для Е-1 (доказ — скрін, не XML)

Скрін списку «Канали» на ширині **1440**: [`p6_17_backends_list_1440.png`](screenshots/p6_17_backends_list_1440.png)

Механічний замір заголовків (Playwright, viewport 1440×900):

|---|---|---|
| `Назва` | 613.5 px | ні |
| `Канал` | 613.5 px | ні |
| `Активний` | 70 px | **ні** |

## Е-2 · UX-16: блокер показано, але кнопку не заблоковано

**Файли:** [`models/channel_provider.py`](../addons/fayna_channel_bridge/models/channel_provider.py), [`views/channel_provider_views.xml`](../addons/fayna_channel_bridge/views/channel_provider_views.xml)

### Що зроблено

1. **Обчислювані поля** на `channel.provider` (метод `_compute_precondition_gate`):
   - `has_unconfirmed_preconditions` (Boolean) — чи є непідтверджені передумови;
   - `blocking_reason` (Char) — людська причина блокування.
   Логіка перевикористовує наявні поля без нових даних:
   - `region_blocklist and not region_confirmed` → `"Підтвердіть, що канал працює поза регіонами: %s"`;
   - `consent_required and not consent_confirmed` → `"Підтвердіть згоду користувача на підключення."`.

2. **Kanban** (галерея): якщо `has_unconfirmed_preconditions` — кнопка «Підключити» рендериться **неактивною** (`btn-secondary`, `disabled="disabled"`), поруч видно іконку замка і `blocking_reason` («Недоступно: …»). Якщо канал підключено — «Відкрити канал»; інакше — активна «Підключити».

3. **Форма каналу**: кнопка «Підключити» в header **прихована** (`invisible="has_unconfirmed_preconditions"`), а причина показана в `alert-danger` з іконкою замка. Нижче — група **«Підтвердження передумов»** з чекбоксами `region_confirmed` і `consent_confirmed`.

4. 🔴 **Серверний захист** у `action_connect` (`models/channel_provider.py:120`): на початку методу
   ```python
   if self.has_unconfirmed_preconditions:
       raise UserError(self.blocking_reason)
   ```
   Схована/неактивна кнопка — не захист: дію можна викликати в обхід UI, тому сервер сам відмовляє з людською причиною.

### Як саме людина підтверджує передумови

Підтвердження робиться **у формі каналу**, не на картці галереї (як і вимагає завдання). Користувач відкриває картку каналу (напр. TikTok), бачить `alert-danger` з причиною «Підтвердіть, що канал працює поза регіонами: ЄЕЗ/ЄС, США», ставить галочку «Підтверджено: працюємо поза забороненими регіонами?» у групі «Підтвердження передумов», зберігає форму — і кнопка «Підключити» стає активною. Для WhatsApp — галочка «Згода користувача отримана?».

### Де стоїть серверна відмова

У `action_connect` (`models/channel_provider.py:120`), **до** відкриття майстра і **до** створення backend. Якщо передумови не підтверджені — `UserError(blocking_reason)`, backend **не** створюється. Це підтверджено трьома новими тестами (див. нижче).

### Verify для Е-2

Три нові тести у [`tests/test_package6_ux.py`](../addons/fayna_channel_bridge/tests/test_package6_ux.py) (клас `TestPackage6PreconditionGate`):

- `test_region_blocklist_without_confirmation_is_blocked` — TikTok (region_blocklist) без підтвердження → `UserError` з текстом «регіонами», backend **не** створено;
- `test_region_blocklist_after_confirmation_passes_gate` — після `region_confirmed=True` той самий виклик проходить гейт (доходить до OAuth «вручну»);
- `test_consent_required_without_confirmation_is_blocked` — WhatsApp (consent_required) без підтвердження → `UserError` з текстом «згоду», backend **не** створено.

Скрін картки TikTok (кнопка неактивна, причина видима поруч): [`p6_06_tiktok_form_blocked.png`](screenshots/p6_06_tiktok_form_blocked.png) (форма) і [`p6_03_gallery_kanban.png`](screenshots/p6_03_gallery_kanban.png) (галерея, картка TikTok з замком і «Недоступно: ЄЕЗ/ЄС, США»).

Механічний доказ (після перезапуску контейнера `web`):
```

  has lock icon: True
  has blocking_reason: True
```
Рендер-скрипт: `tiktok connect btn not clickable (expected)` ✅.

## Е-4 · Різна висота карток між рядами

**Файл:** [`views/channel_provider_views.xml`](../addons/fayna_channel_bridge/views/channel_provider_views.xml)

### Рішення: вирівнювання в межах ряду (стандартна поведінка kanban), міжрядове — відхилено

Механічний замір висот карток галереї (Playwright):

| Картка | Висота |
|---|---|
| Telegram | 285.5 px |
| Messenger | 285.5 px |
| Instagram | 285.5 px |
| WhatsApp | 285.5 px |
| Viber | 214.5 px |
| TikTok | 214.5 px |
| LiveChat | 214.5 px |

**У межах кожного ряду висоти однакові** (285.5 у першому, 214.5 у другому) — це стандартна поведінка Odoo kanban (flexbox вирівнює картки одного ряду). Різниця між рядами (71 px) — через довжину опису: у першому ряду довші описи (Telegram/Messenger/Instagram/WhatsApp), у другому коротші (Viber/TikTok/LiveChat).

**Чому міжрядове вирівнювання відхилено:** за завданням, якщо вирівнювання вимагає фіксованої висоти — **не робити**, бо це обрізає контент на картці з довгим описом. Примусове вирівнювання всіх карток до висоти найвищої (285.5) створило б порожні зони на коротких картках другого ряду; примусове до найнижчої (214.5) — обрізало б описи першого ряду. Тож лишаємо стандартну поведінку kanban: **рівні ряди, нерівні між рядами, жоден опис не обрізано**.

### Verify для Е-4 (доказ — скрін)

Скрін галереї: [`p6_03_gallery_kanban.png`](screenshots/p6_03_gallery_kanban.png). Висоти карток у межах ряду узгоджені, жоден опис не обрізано (опис обрізається лише стандартним `line-clamp` до 2–3 рядків, без втрати сенсу). ✅
